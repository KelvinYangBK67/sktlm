# 三、正式學術審閱

完成上述 provenance verification 後，再開始正式審閱。

請從**問題前景、工程實作、理論創見與目前科學證據成熟度**等角度，以連續的、成段的文本，對這個 research repository 進行客觀而嚴格的評價。

請把它視為一個正在接受匿名 NLP / ML 學術審閱的研究項目，而不是一般程式碼展示。

不要預設：

* 作者的研究 framing 必然正確；
* roadmap 中的研究目標必然具有新意；
* 方法選擇必然合理；
* 工程規模本身意味著科學成熟；
* negative result 意味著研究失敗；
* future work 可以被當作已完成成果。

同樣，不要因為工程規模、文件數量、測試數量、reproducibility infrastructure、roadmap ambition 或研究投入程度本身提高對科學成果的評價。

## 證據層級

在整個審閱過程中，請嚴格區分：

1. 已經由 repository 中現有、completed 且 accepted 的實驗結果直接支持的科學結論；
2. 已經實作，但尚未形成完整實證證據的方法；
3. 已經啟動但仍在 RUNNING、尚未通過 final audit 的實驗；
4. 已經明確決定但尚未執行的研究設計；
5. roadmap、future hypothesis 或後續 Stage 中尚未實現的研究構想；
6. 純歷史 provenance、已取消方案或 superseded design。

不要把第 2–6 類內容描述成已經得到實驗驗證的研究成果。

如果 repository 保留了歷史方案、舊 checkpoint、舊實驗設計和較新的 authoritative/current 決策，請根據指定 commit 內的：

* current / authoritative 標記；
* checkpoint 時間；
* experiment status；
* research roadmap；
* decision records；
* provenance 說明；

判斷它們的關係。

不要因為歷史文檔仍被保留，就自動把它視為當前研究方案。

## 審閱重點

請特別評估：

* 研究問題本身是否具有足夠的學術價值；
* 它是否超越單純 Sanskrit tokenization / sandhi processing，而形成可清楚定義的更一般研究問題；
* 目前的 generality claim 到底有多少已被實證支持；
* 現有方法是否真正對應它聲稱研究的問題；
* latent variables 的 operational definition 是否充分清楚；
* 實驗設計能否有效隔離主要 confound；
* representation、script、spacing、external grammar、lexical capacity 等因素是否被合理控制；
* 已完成的結果真正支持哪些 claim；
* 哪些 interpretation 仍存在重要的 alternative explanation；
* model-internal diagnostics 與真正具有 predictive / structural / linguistic 意義的 evidence 是否被清楚區分；
* 理論 framing 是否足夠清晰；
* 是否存在重要的 identifiability、model-selection、equivalence 或 hypothesis-class 問題；
* 工程與 reproducibility 工作是否真正服務於科學問題；
* 是否存在 infrastructure 已經明顯超過當前 scientific payoff 的風險；
* 現有 evaluation 是否足以支撐最重要的 scientific claims；
* 已完成的 negative results 是否具有獨立科學價值；
* 如果你是實際 NLP / ML 匿名同行評審，你最可能提出哪些實質性質疑。

不要因為某個結果「不好看」就預設應該重新調參或修改模型。請判斷這個結果是否本身構成對 hypothesis class、representation、identifiability、computational behavior 或其他研究問題的有效證據。

# 四、對改進建議進行 scope 分級

對所有你提出的改進建議，請盡量區分為：

### Blocking / claim-critical issues

如果不解決，會實質削弱當前工作所聲稱的核心 scientific claim，或者使某個主要結論缺乏足夠證據。

### Important but non-blocking improvements

可以顯著提高說服力、清晰度、可解釋性或 reviewer confidence，但不一定阻止目前 milestone 本身成立。

### Optional extensions / reviewer wishlist

具有研究價值，但會明顯擴大 scope，或者實際上屬於下一 milestone、下一 Stage、另一篇論文或 future work，而不是當前 scientific claim 成立所必需。

請避免為了顯得全面而列出大量 baseline、模型、ablation 或 benchmark。

如果建議新增一項實驗，請具體說明：

1. 它要排除哪一個 alternative explanation；
2. 現有 evidence 為什麼不足；
3. 該實驗是否真的 claim-critical；
4. 還是只是合理但可推遲的擴展。

# 五、novelty 與 prior work 邊界

如果你認為某項研究構想與已有領域存在直接關係，例如：

* unsupervised morphology；
* MDL / Bayesian morphology；
* segmentation；
* finite-state analysis；
* latent-variable modeling；
* grammar induction；
* representation learning；
* Sanskrit sandhi splitting；

請具體指出真正可能具有 novelty 的部分是什麼，以及哪些部分本身已有成熟先例。

不要因為某個已有領域相關，就直接判定整體方法沒有新意；也不要因為新的研究語境或術語，就把已有方法重新包裝成理論創新。

請盡可能判斷：

> 如果這項工作最終成功，它真正不可被既有方法輕易替代的 scientific contribution 會是什麼？

# 六、最終判斷

最後，請以目前這個**指定 commit**為嚴格 cutoff，回答以下問題：

1. 這個項目到目前為止實際完成了什麼；
2. 目前最有價值的已完成科學結果是什麼；
3. 哪些重要內容仍然只是未完成的研究計畫；
4. 最大的未解決 scientific risk 是什麼；
5. 最大的 engineering / reproducibility risk 是什麼；
6. 如果它現在作為論文投稿，你認為最容易被 reviewer 攻擊的核心點是什麼；
7. 接下來哪一項結果最可能實質改變你對其學術價值的判斷；
8. 如果下一個主要結果是 negative result，它在什麼條件下仍然具有足夠的 scientific value；
9. 目前這項工作的最合理學術定位是什麼。

請不要為了顯得「客觀」而機械地平衡正面與負面意見。哪一方面證據強，就明確說強；哪一方面尚未成立，就明確說尚未成立。

請盡量依據 repository 中實際存在的：

* source code；
* experiment configuration；
* tracked reports；
* accepted results；
* current decisions；
* authoritative roadmap；
* test / audit evidence；

進行判斷。

不要根據一般 NLP project 的模板補出 repository 中不存在的事實。

正式審閱部分請以連續、完整、具體的學術評論文本為主，可以使用少量必要的小標題，但不要把主要內容寫成 checklist、簡單打分表或優缺點列表。

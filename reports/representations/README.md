# Formal GRETIL Representations: Technical Construction and Validation Report

This document records the construction, semantics, provenance, implementation constraints, and validation of the six formal GRETIL text representations used by `sktlm`.

The representation layer is strictly downstream of the frozen canonical corpus. It does not perform corpus cleaning, textual emendation, desandhi, morphological analysis, or inferred segmentation. Its only purpose is to derive controlled experimental realizations of the same canonical Sanskrit corpus along two axes:

1. script; and
2. lexical spacing.

The current formal representation implementation is:

```text
canonical-representations-3
```

---

## 1. Authoritative input

All formal representations are derived from the frozen pre-M0 canonical GRETIL corpus:

```text
data/canonical/gretil_iast
```

The authoritative canonical manifest is:

```text
data/manifests/canonical_corpus.csv
```

The canonical freeze contains:

```text
documents:       240
characters:      57,588,079
bytes:           69,864,279
corpus SHA256:   9c515ca46ad8f9fca7e879c0a1617207bf5ccf3df21930aaa0995227c3942c40
```

This SHA256 is also used as the representation `freeze_id`.

Representation generation never writes back into the canonical corpus. Every derived representation remains cryptographically linked to the canonical document from which it was generated.

Detailed corpus-cleaning provenance is documented separately in:

## 2. Formal experimental matrix

The formal representation layer crosses two scripts with three lexical-spacing conditions.

| Script | Spacing condition | Meaning |
| --- | --- | --- |
| IAST | `surface_word` | canonical lexical spacing |
| IAST | `legacy_joined` | selected historical joining rules |
| IAST | `continuous` | lexical whitespace removed |
| Devanagari | `surface_word` | canonical lexical spacing after script realization |
| Devanagari | `legacy_joined` | selected historical joining rules after script realization |
| Devanagari | `continuous` | lexical whitespace removed with valid Devanagari recomposition |

The resulting directory layout is:

```text
data/representations/gretil/
├── iast/
│   ├── surface_word/
│   ├── legacy_joined/
│   └── continuous/
└── devanagari/
    ├── surface_word/
    ├── legacy_joined/
    └── continuous/
```

With 240 canonical documents, this produces:

```text
240 documents
× 2 scripts
× 3 spacing conditions
= 1,440 representation files
```

Only these six datasets are part of the formal experiment.

The representation library may retain older or auxiliary condition names such as `observed` or `lexical_boundary` for compatibility or future work, but they are not generated by the formal GRETIL representation pipeline.

## 3. Separation of experimental dimensions

The representation system distinguishes three conceptually different operations:

```text
canonical textual identity
        ↓
script realization
        ↓
lexical-spacing manipulation
        ↓
script-specific punctuation realization
```

These operations are kept separate deliberately.

The script axis controls how the same Sanskrit text is encoded orthographically.

The spacing axis controls the availability of lexical/inter-word whitespace.

Script-specific punctuation typography, especially Devanagari daṇḍa attachment, is treated as an orthographic convention rather than as a lexical-spacing manipulation.

This distinction is important because the spacing experiment is designed primarily to manipulate boundaries relevant to inter-word Sanskrit phonology and tokenization, not arbitrary whitespace surrounding punctuation.

---

## 4. Script realization

### 4.1 IAST

The IAST branch uses the canonical text directly.

For `iast/surface_word`, output bytes are required to be identical to the corresponding canonical input bytes.

This condition therefore serves both as a formal experimental representation and as an identity check on the representation pipeline.

---

### 4.2 IAST to Devanagari

Devanagari is generated mechanically from canonical IAST.

The transliterator supports the Sanskrit inventory used by the corpus, including:

```text
vowels
consonants
anusvāra
visarga
avagraha
single daṇḍa
double daṇḍa
```

Representative mappings include:

```text
a   → अ
ā   → आ
i   → इ
ī   → ई

k   → क
kh  → ख
g   → ग

ṃ   → ं
ḥ   → ः
'   → ऽ

|   → ।
||  → ॥
```

Dependent vowels are realized with normal Devanagari vowel marks when they occur directly after a consonant.

A consonant not followed by a vowel receives virāma.

For example:

```text
tat tvam asi
```

is script-realized as:

```text
तत् त्वम् असि
```

Script conversion by itself does not perform lexical joining.

Before any spacing condition is applied, the generator verifies that raw script conversion has preserved the whitespace signature of the canonical IAST text.

---

## 5. Orthographic conversion versus character substitution

IAST-to-Devanagari conversion is treated as orthographic realization, not as literal code-point substitution.

A usable Devanagari corpus should respect stable conventions of the Devanagari writing system even where they do not preserve punctuation-adjacent ASCII spaces from IAST literally.

The most important case is daṇḍa typography.

For example, an intermediate transliteration corresponding to:

```text
rāmaḥ | sītā
```

may contain:

```text
रामः । सीता
```

but the formal Devanagari realization is:

```text
रामः। सीता
```

The deleted space is between lexical material and punctuation. It is not a word-to-word boundary and therefore does not modify the sandhi-related lexical-spacing variable.

This convention is applied uniformly to all three formal Devanagari conditions.

---

## 6. Spacing condition: `surface_word`

`surface_word` is the condition with maximal preservation of observed lexical whitespace.

### 6.1 IAST

IAST `surface_word` is byte-identical to the canonical corpus.

No lexical space is inserted, removed, inferred, or reconstructed.

For every document:

```text
iast/surface_word == canonical IAST
```

at the byte level.

---

### 6.2 Devanagari

Devanagari `surface_word` preserves all lexical spacing inherited from the canonical text after script conversion.

The only systematic whitespace change is script-specific daṇḍa typography.

For example:

```text
rāmaḥ gacchati | sītā tiṣṭhati ||
```

is realized as:

```text
रामः गच्छति। सीता तिष्ठति॥
```

rather than:

```text
रामः गच्छति । सीता तिष्ठति ॥
```

No ordinary lexical spaces are otherwise deleted.

---

## 7. Spacing condition: `legacy_joined`

`legacy_joined` reproduces the restricted joining behavior used in earlier project preprocessing as an explicit experimental condition.

It is not a general sandhi algorithm.

It removes an existing lexical space only when the local boundary satisfies one of three predefined classes:

```text
C + space + C
C + space + V
V + space + avagraha
```

where:

```text
C = consonant
V = vowel
```

For IAST, the apostrophe used for avagraha participates in the third rule.

Examples:

```text
tat tvam asi
→ tattvamasi
```

and:

```text
a 'sti
→ a'sti
```

---

### 7.1 Consonant classification

The joining rule uses an explicit Sanskrit consonant inventory, including aspirated digraphs such as:

```text
kh gh ch jh ṭh ḍh th dh ph bh
```

Anusvāra and visarga are deliberately not classified as consonants for this rule.

Therefore:

```text
aṃ ka
```

remains:

```text
aṃ ka
```

and:

```text
aḥ a
```

remains:

```text
aḥ a
```

This prevents the historical joining condition from being generalized beyond its intended behavior.

---

### 7.2 Devanagari C+C joining

When a Devanagari word ends in a virāma-marked consonant and the next word begins with a consonant, removing the boundary naturally produces the corresponding consonant sequence.

For example:

```text
तत् त्वम्
```

becomes:

```text
तत्त्वम्
```

No separate linguistic sandhi analysis is involved.

---

### 7.3 Devanagari C+V joining

A Devanagari consonant-plus-vowel boundary requires orthographic recomposition rather than simple whitespace deletion.

For example:

```text
द् + अ
```

must become:

```text
द
```

rather than:

```text
द्अ
```

Similarly:

```text
द् + इ → दि
द् + ई → दी
द् + उ → दु
द् + ए → दे
```

The `legacy_joined` implementation therefore removes the preceding virāma and realizes the following independent vowel as the appropriate vowel mark, or as inherent `a` where appropriate.

This is orthographic recomposition of a boundary already selected by the experimental rule. It is not sandhi reconstruction.

---

## 8. Spacing condition: `continuous`

`continuous` removes lexical/inter-word whitespace as completely as possible while retaining physical line boundaries and script-specific daṇḍa structure.

It is not defined as deletion of every whitespace character in the document.

Physical LF boundaries are preserved.

For example:

```text
devaś ca rāmaś ca
dhāvanti iti
```

becomes:

```text
devaścarāmaśca
dhāvantiiti
```

rather than one document-wide unbroken string.

---

## 9. IAST `continuous`

Ordinary lexical whitespace is deleted.

IAST daṇḍas remain structurally separated from adjacent same-line text.

For example:

```text
rāmaḥ gacchati | sītā tiṣṭhati
```

becomes:

```text
rāmaḥgacchati | sītātiṣṭhati
```

and:

```text
rāmaḥ gacchati ||
```

becomes:

```text
rāmaḥgacchati ||
```

If text is present before the daṇḍa on the same line, one ASCII space is retained before `|` or `||`.

If text follows on the same line, one ASCII space is retained after it.

No trailing space is introduced at line end.

These spaces are structural punctuation separators rather than retained lexical word boundaries.

---

## 10. Devanagari `continuous`

Devanagari `continuous` removes lexical whitespace while preserving valid Devanagari orthography.

For example:

```text
रामः गच्छति । सीता तिष्ठति
```

becomes:

```text
रामःगच्छति। सीतातिष्ठति
```

and:

```text
रामः गच्छति ॥
```

becomes:

```text
रामःगच्छति॥
```

The condition retains:

```text
no space before । or ॥
one space after । or ॥ when same-line text follows
no trailing whitespace after a line-final daṇḍa
```

---

## 11. Devanagari continuous boundary recomposition

### 11.1 Failure discovered in the previous implementation

An earlier version of the formal representation pipeline derived Devanagari `continuous` by:

```text
canonical IAST
→ Devanagari surface form
→ delete lexical spaces
```

Simple deletion is insufficient for Devanagari because script realization depends on whether a consonant and following vowel are separated by a boundary.

Consider an IAST sequence equivalent to:

```text
tad abhyasrāmyad abhyatapat samatapat
```

Its normal spaced Devanagari realization contains:

```text
तद् अभ्यस्राम्यद् अभ्यतपत् समतपत्
```

At the first boundary:

```text
द् + space + अ
```

the consonant is represented with virāma because the vowel begins a separate orthographic word.

Naively deleting the space therefore produced the malformed sequence:

```text
द्अ
```

and resulted in output such as:

```text
तद्अभ्यस्राम्यद्अभ्यतपत्समतपत्
```

This is not a valid continuous Devanagari realization of the intended character sequence.

The issue did not affect canonical IAST. It was a downstream representation-generation error.

---

### 11.2 Corrected behavior

`canonical-representations-3` corrects this problem.

When `continuous` removes a Devanagari lexical boundary, the implementation checks whether deletion creates the structure:

```text
consonant + virāma + independent vowel
```

If so, it performs the corresponding Devanagari graphemic recomposition:

```text
C् + अ → C
C् + आ → Cा
C् + इ → Cि
C् + ई → Cी
C् + उ → Cु
C् + ऊ → Cू
C् + ऋ → Cृ
...
C् + ए → Cे
C् + ऐ → Cै
C् + ओ → Cो
C् + औ → Cौ
```

Thus:

```text
तद् अस्ति
→ तदस्ति
```

```text
तद् इति
→ तदिति
```

```text
तद् उक्तम्
→ तदुक्तम्
```

```text
तद् एव
→ तदेव
```

and the originally observed failure is correctly realized as:

```text
तदभ्यस्राम्यदभ्यतपत्समतपत्
```

rather than:

```text
तद्अभ्यस्राम्यद्अभ्यतपत्समतपत्
```

---

### 11.3 Methodological interpretation

This recomposition does not introduce lexical analysis or sandhi.

The lexical boundary has already been removed by definition of the `continuous` condition.

The additional operation merely realizes the resulting character sequence in normal Devanagari orthography.

In other words:

```text
spacing manipulation decides that the boundary disappears
orthographic recomposition decides how the resulting Devanagari sequence is written
```

These are distinct operations.

The correction therefore preserves the intended experimental variable rather than adding a new linguistic transformation.

## 12. Devanagari daṇḍa convention

All formal Devanagari conditions share one punctuation convention.

Whitespace immediately before:

```text
।
॥
```

is removed.

If ordinary text follows on the same line, exactly one ASCII space follows the daṇḍa.

If the daṇḍa is line-final, no trailing space is generated.

Thus:

```text
रामः गच्छति । सीता तिष्ठति ॥
```

is normalized as:

```text
रामः गच्छति। सीता तिष्ठति॥
```

in `surface_word`.

The same punctuation convention is applied after lexical joining in `legacy_joined` and after lexical-space removal in `continuous`.

This operation is deliberately narrow.

The formal pipeline does not call the older general-purpose:

```text
normalize_devanagari_text()
```

helper.

That function performs broader whitespace and document normalization that belongs upstream of the formal representation stage.

The canonical corpus has already undergone those operations.

---

## 13. Operations deliberately excluded

Formal representation generation performs no:

```text
desandhi
morphological segmentation
compound segmentation
word-boundary inference
phonological correction
spelling correction
source reconstruction
automatic Sanskrit emendation
```

No representation attempts to recover an underlying morphologically or historically idealized Sanskrit sequence.

`surface_word` uses observed canonical spacing.

`legacy_joined` applies only the explicitly defined local joining rules.

`continuous` removes lexical spacing mechanically and performs only the orthographic recomposition necessary to realize the resulting Devanagari sequence correctly.

---

## 14. Representation generation architecture

For each canonical document, the generator:

1. reads the frozen canonical IAST document;
2. verifies correspondence with the canonical manifest;
3. derives the requested script;
4. checks that script conversion itself preserves the whitespace signature;
5. applies one of the three formal spacing conditions;
6. applies the narrow Devanagari daṇḍa convention where relevant;
7. writes the representation file;
8. computes its SHA256;
9. records provenance and size metadata in the representation manifest.

The formal generation dimensions are fixed as:

```text
scripts:
    iast
    devanagari

conditions:
    surface_word
    legacy_joined
    continuous
```

The generator refuses to generate into an already existing formal output root, preventing accidental mixing of representations from different runs.

## 18. Formal validation

The representation validator checks substantially more than file counts.

### 18.1 Membership

The expected row count is:

```text
canonical document count
× number of formal scripts
× number of formal spacing conditions
```

For the current corpus:

```text
240 × 2 × 3 = 1440
```

Each:

```text
(script, condition, relative_path)
```

combination must be unique.

---

### 18.2 Freeze consistency

Every representation row must contain the same canonical `freeze_id`.

Mixing representation files derived from different canonical freezes is rejected.

---

### 18.3 Path containment

Every representation path must resolve inside the configured representation output root.

This prevents malformed or stale manifest paths from escaping the intended corpus tree.

---

### 18.4 Hash validation

Every representation file must exist and its SHA256 must equal its recorded:

```text
representation_hash
```

---

### 18.5 Deterministic regeneration

For every manifest row, validation independently recomputes the representation from the canonical text using the current formal script and spacing functions.

The validator then compares the resulting bytes against the stored representation file.

Thus validation establishes both:

```text
file integrity
and
derivational correctness
```

rather than merely checking that the manifest and file agree with each other.

---

### 18.6 IAST identity invariant

Every:

```text
iast/surface_word
```

file must be byte-identical to its corresponding canonical document.

Any difference is a validation failure.

---

### 18.7 Boundary-sidecar exclusion

Formal output must contain no:

```text
*.boundaries.jsonl
```

files.

Boundary metadata in manifest rows must also be empty, with:

```text
boundary_count = 0
```

## 23. Experimental interpretation

The six datasets are not six independently edited corpora.

They are deterministic experimental views of one canonical corpus:

```text
                         canonical M0
                              |
                 same documents and identity
                              |
                +-------------+-------------+
                |                           |
               IAST                     Devanagari
                |                           |
        +-------+-------+           +-------+-------+
        |       |       |           |       |       |
      SW       LJ      CONT        SW      LJ      CONT
```

where:

```text
SW   = surface_word
LJ   = legacy_joined
CONT = continuous
```

The spacing axis can be interpreted as progressively reducing explicit lexical-boundary information:

```text
surface_word
    observed canonical lexical whitespace retained

legacy_joined
    selected historically motivated lexical boundaries removed

continuous
    lexical whitespace removed globally
```

The script axis compares two orthographic realizations of the same canonical material:

```text
IAST
versus
Devanagari
```

The resulting experimental design therefore permits analysis of:

```text
script effects
spacing effects
script × spacing interactions
```

while holding canonical document identity and corpus membership fixed.

---

## 24. Methodological boundary

The formal representation layer must remain downstream and one-way.

The dependency is:

```text
canonical corpus
      ↓
representations
      ↓
tokenizers
      ↓
models and evaluation
```

Experimental findings must not silently mutate the canonical corpus or retroactively redefine the formal representation rules.

If a reproducible implementation defect is discovered, as occurred with the original Devanagari continuous C+V realization, it must be corrected explicitly as a new representation implementation revision and all affected derived artifacts must be regenerated.

This is why the corrected implementation is recorded as:

```text
canonical-representations-3
```

rather than silently retaining the previous implementation identity.

## 25. Final formal definition

The formal pre-M0 representation family consists exactly of:

```text
IAST × surface_word
IAST × legacy_joined
IAST × continuous

Devanagari × surface_word
Devanagari × legacy_joined
Devanagari × continuous
```

All six:

- contain the same 240 canonical documents;
- derive from the same frozen corpus identity;
- preserve physical line structure;
- perform no inferred linguistic segmentation;
- have deterministic generation rules;
- are recorded in a cryptographic manifest;
- pass deterministic regeneration validation;
- are suitable as fixed inputs for the subsequent tokenizer experiments.

At this point, the representation layer is considered closed for the pre-M0 experimental stage.
